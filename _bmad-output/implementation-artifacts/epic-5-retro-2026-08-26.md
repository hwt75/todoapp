## Findings

### A — Diff-scope review (`code-review`, high effort, 8 finder angles + verification)

Run against the full epic diff, weighted toward the boundaries between the four stories. Full
detail already reported via `ReportFindings`; summarized here with disposition.

**Confirmed, open, correctness — all three independently re-verified by direct code inspection,
not only subagent claim:**

1. **`mark_penalty_collected()` never took the advisory lock its own fix claimed to add.**
   `supabase/migrations/20260825120000_the_same_lock_the_same_day.sql:130-181`. The migration's
   header comment and `deferred-work.md` both assert the per-account
   `pg_advisory_xact_lock(hashtext(owner_id::text))` was added to *both*
   `appeal_hold_penalty()` and `mark_penalty_collected()` — reading the actual function bodies,
   only `appeal_hold_penalty()` (line 54) took it. `mark_penalty_collected()`'s own
   `grace_day`-existence guard is an unlocked `SELECT`. **Live in production** since 2026-08-25 —
   this migration is already pushed. A referee collecting a Penalty at the same instant a
   `grace_day` insert validates that day as still `owed` can still let both commit, wasting one
   of the account's two non-carrying monthly Grace Days for nothing — the exact failure class
   this migration's own commit message says it closed.
2. **`enqueue_gate_reminders()` silently dropped Story 2.9's "Day N is waiting" chain-stake
   copy.** `supabase/migrations/20260826090000_the_app_notices_ive_gone_quiet.sql:118` (and
   inherited unchanged by `20260826100000`'s own replacement). Confirmed by direct grep: `lone_
   commitment`/`lone_chain`/`stake` exist only in `20260819261000_gate_names_the_chain.sql`, gone
   from both Epic-5 `create or replace` bodies. Story 5.2's rewrite appears to have branched off
   a version of the function that predates Story 2.9. A doer with exactly one outstanding Daily
   commitment and a running chain no longer sees "Day 12 is waiting." in the gate-reminder push —
   only the bare unanswered-count sentence. **Live in production.**
3. **Monthly report's Incurred figure (SM-C1) and the Failed-day set behind SM-2 can
   silently misattribute to the wrong month.** Root cause verified directly:
   `apply_grace_days()` (`supabase/migrations/20260825110000_a_countable_way_to_be_forgiven.sql:
   446-447`) inserts a *new* penalty row, already `waived`, with a fresh `created_at` at fold-in
   time — not the original Failed Day's own timestamp — tied to a *new* corrective settlement
   that supersedes the original. `penalty_current`/`settlement_current` show only the
   non-superseded row, so the original penalty and its `verdict = 'failed'` settlement vanish
   from their own month's figures entirely the moment a Grace Day (or an approved Appeal — same
   supersession mechanism) lands, however late. This is new exposure: nothing before Story 5.4
   read `penalty_current.created_at`/`settlement_current.verdict` this way. **This finding
   undercuts Story 5.4's own reason for existing** — FR-24 is explicitly "a mechanism that has
   quietly died cannot keep looking like one that is working," and this is exactly that failure
   mode, inside the tool built to catch it.

**Plausible, open, correctness:**

4. **Silence intervention has zero navigation when nothing is currently pending.**
   `components/silence-intervention.tsx:36`. When an episode is active and `owing.length === 0`,
   the screen renders only static text and a Grace Days sentence — no `MorningGate` (gated on
   `pending`), no Settings/Ledger link, no sign-out, no Grace Day spend control. The episode can
   only close via a Declaration insert, and there is nothing to declare in this state — the doer
   is stuck until some later day's commitment happens to become owing again.

**Plausible, open, reuse/altitude (lower severity, real maintenance debt):**

5. Grace Day spend logic (state, mutation, JSX) duplicated wholesale between
   `components/today.tsx` and `components/ledger.tsx` (comments admit the mirroring rather than
   sharing a hook).
6. `grace_allowance_remaining` fetch-and-fail pattern copy-pasted 4× (`today.tsx`, `ledger.tsx`,
   `settings.tsx`, `silence-intervention.tsx`), including an identical literal error string.
7. `lib/monthly-report.ts:304` (`foldPenaltyFigure`) reimplements `lib/money.ts`'s `totalOwed()`
   with a bare `reduce`, losing that helper's amount validation.
8. `supabase/migrations/20260819241000_expiry_and_supersession.sql:31` — `settlement_current` is
   still `select s.*`, the identical pattern that just froze `penalty_current`'s column list and
   forced this epic's own elaborate spelled-out-columns fix. The next story to add a column to
   `settlement` will hit the same Postgres 42P16 error, with a wider blast radius
   (`chain_current` and `penalty_current` both depend on `settlement_current`).
9. `app/page.tsx:47` — 6 independent `useState` booleans/objects manage overlay navigation with
   no type-level mutual exclusion; correctness depends entirely on ternary-branch ordering. This
   file has gained one new overlay per recent story.
10. `supabase/functions/email-worker/index.ts` duplicates `outbox-worker`'s `mark()`/`json()`
    and the migration's `wake_email_worker()` duplicates `wake_outbox_worker()` almost verbatim —
    no shared helper despite the code's own comments saying it "mirrors... exactly."

### B — God-class / size growth

Ranked the diff's highest-churn files (`lib/monthly-report.ts` 427 added lines,
`supabase/tests/5-1-...sql` 622, `supabase/migrations/20260825110000` 507, two new SQL test
files >400 each) and read each one's current real size. All new files are large because they are
verbose, heavily-commented migrations and SQL test files — this codebase's established style
throughout, not a growth pattern unique to Epic 5. Checked the highest-churn *pre-existing* files
this epic modified: `app/page.tsx` (278 lines), `lib/referee.ts` (454, across two stories),
`components/today.tsx` (325), `components/ledger.tsx` (342) — none past a size this codebase's
own density would call alarming. **No god-class finding.** `app/page.tsx`'s growing ternary
(finding 9 above) is a structural concern, not a size one.

### C — Pattern divergence

No divergence from established conventions found beyond what's captured in findings 5–10 above
(duplication is the dominant divergence pattern this epic shows, not naming/error-handling/test-
structure divergence). Every migration in the epic correctly followed the "additive, never edit
a past migration file" discipline (`drop function` + `create function` for signature changes,
`create or replace` for same-signature replacement, `alter table add column` for schema growth) —
except for the two "replace the whole function body" cases (findings 1–2) where the *base*
being replaced from was stale, not the discipline itself being violated.

**What was exercised:** automated only, for all four stories — no manual browser click-through
happened anywhere in this epic. Concretely: every `supabase/tests/*.sql` file (26 total,
including all four of this epic's own) run against a freshly reset real local Postgres via

reproduced) and after (fix confirmed) the patch — the one point in this epic where "behavior"
was checked against the real deployed system rather than only the local stack or unit tests.

**What was not exercised:** no story in this epic was clicked through in a real browser. This
gap is self-disclosed in Story 5.1's own spec ("Not run in this environment... the actual
click-through of spending a Grace Day and watching the Ledger row update") and holds equally for
5.2's Silence intervention, 5.3's Referee escalation email (no real email has been observed to
actually arrive — Resend delivery was configured and deployed in this session but never watched
end-to-end), and 5.4's Monthly report screen. The SQL-level and unit-level verification is real
and extensive, but it is not the same claim as "a person opened the app and saw this work."

## Acceptance verdict

**accepted-with-open-items.** Criteria: **declared** (FR-16/17/18/24, each story's own frozen
Intent + Acceptance Criteria). All four stories are `done`; the epic delivers real, working
functionality confirmed by extensive automated verification, including one direct live-database
check. It is not **accepted** outright because three **confirmed, currently open** defects
remain from the diff-scope review (A1–A3) — two of them live in production right now, and one
(A3) directly undermines the Monthly report's own stated purpose. It is not **rejected** because
none of the three is architecturally invasive: each has a narrow, well-understood fix (a missing
lock statement; restoring dropped copy; a reporting-query redesign that does not touch the
underlying schema), no story's individual acceptance criteria are in question, and nothing here
indicates rework of the epic's actual design. Action items 1–4 above are the condition for a
clean **accepted** status; they should be treated as near-term work, not indefinitely deferred.
