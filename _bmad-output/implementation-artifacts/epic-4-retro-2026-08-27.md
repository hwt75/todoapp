### A — Diff-scope review (`bmad-review`, 3 lenses: adversarial, edge-case-hunter,

Verification-gap was further split into three parallel seam investigations by its own subagent

subagent report, per this skill's own rule that sub-agent findings are unverified reports until
checked against the primary source).

**Re-scoped after deeper investigation — process lesson, not an Epic-4-specific fix:**

1. **`file_auto_check_result()`'s `missed` branch reads `commitment.carries_penalty` live, at
   the hourly `resolve_auto_checks()` pass, not frozen as of the claimed day.**
   `supabase/migrations/20260824120000_a_slip_the_machine_filed_is_not_a_slip_he_typed.sql:92-96`
   — confirmed by direct read: `select c.carries_penalty into v_carries_penalty from
   public.commitment c where c.id = p_commitment_id`, evaluated at filing time. The adversarial
   lens flagged this as an Epic-4-specific, fix-now defect: an author who anticipates a
   machine-filed miss could toggle `carries_penalty` off before the hourly pass runs, then back
   on, filing nothing for that day.
   **Correction, found while scoping the fix (not by any lens):** this is not new to Epic 4 and
   not a narrower problem than the base mechanism already has. `commitments_owing()`
   (`supabase/migrations/20260819220000_settlement.sql:68-75`) — the shared base view
   `settle_day()`/`settle_week()` both read from — joins `commitment.carries_penalty` exactly as
   live, and `settle_day` doesn't run until `declaration_deadline` (up to ~71 hours after the
   day, per `20260824100000...sql`'s own comment), a **wider** toggle-window than
   `resolve_auto_checks()`'s ~1-24 hour one. So an author could already defeat a plain
   admitted/silent miss's Penalty the same way, for any commitment, Auto-check or not, since
   `settle_day()` itself shipped in Epic 2. Freezing `carries_penalty` only for the Auto-check
   path would not close the actual concern (an author can just as easily rely on an ordinary
   miss instead of an Auto-check one) and would leave the read inconsistent between
   `file_auto_check_result()` and `commitments_owing()`. Properly closing this needs a real
   design decision — a `carries_penalty` snapshot/versioning mechanism spanning
   `commitments_owing()`, `settle_day()`, `settle_week()`, `file_auto_check_result()`, and
   `appeal_hold_penalty()` — which is an architecture question for Epics 2-4 collectively, not
   an Epic-4 patch. **Human decision (2026-08-27): downgrade to a process lesson for a future
   design session; do not patch Auto-check's read alone.** No code change made for this finding
   in this pass.

   **Superseded later the same day.** The human asked for the system-wide design after all;
   implemented and verified live in `supabase/migrations/20260827130000_carries_penalty_freezes_by_day.sql`
   — a new `commitment_carries_penalty_change` append-only history table plus
   `carries_penalty_as_of(commitment_id, day)`, wired into `commitments_owing()`,
   `file_auto_check_result()`, and `settle_week()`'s own independent Weekly Quota
   `carries_penalty` read (a fourth live-read site found only while implementing this fix — not
   caught by any lens, since it never appeared in the original diff-scope review's own
   `commitments_owing()`-centric framing). `appeal_hold_penalty()` deliberately left unchanged,
   per the same human decision. Verified against the real database (rolled back) in both
   directions — a toggle after the fact never erases a genuine charge nor invents one — and
   against the one pre-existing test file that backdates a Weekly Quota commitment's own
   `created_at` (`3-4-week-settlement.sql`), which required a second design refinement
   (`carries_penalty_as_of()` falls back to the *earliest* known value for a day before any
   tracked history exists, rather than NULL/false) to keep passing. See
   `supabase/tests/carries_penalty_freezes_by_day.sql`.
2. **FR-2a's own documented invariant — "Turning a Penalty off on a commitment with a pending
   Appeal resolves that Appeal in the author's favor immediately" (`epic-4-context.md:39`) —
   has no implementation anywhere.** Confirmed directly: the only trigger on `public.commitment`
   in the whole schema is `commitment_touch_updated_at`
   (`supabase/migrations/20260819150000_commitment.sql:118-119`); nothing reacts to
   `carries_penalty` flipping to `false`. **Converged independently across three lens
   passes** (adversarial, edge-case-hunter, and the precedence→appeal-hold verification-gap
   seam), which is a strong signal on its own. The verification-gap seam additionally found that
   `deferred-work.md`'s entry dismissing this exact hazard rests on a **factually false
   premise** — it states "no UI path exposes editing `carries_penalty` post-creation," but
   `commitment-form.tsx` renders as an editable "Edit commitment" form (including the money
   checkbox) whenever `initial` is supplied, and `commitment-list.tsx` saves that edit straight
   through. Today: the Held Penalty just sits on the ordinary ruling/timeout path regardless of
   the toggle, and if the referee rules "He didn't" first, it converts to `owed` on a commitment
   that no longer carries money at all.
3. **FR-14's "evidence must be dated the claimed day" requirement is entirely unimplemented.**
   Confirmed directly: no date/EXIF column on `appeal_evidence`
   (`supabase/migrations/20260824130000_contest_a_miss_the_machine_got_wrong.sql:237-257` has
   only `id, appeal_id, owner_id, storage_path, created_at`), no client-side check
   (`components/appeal-form.tsx`'s file input only sets `accept="image/*"`, never reads
   `file.lastModified`), no server-side check. **Converged independently across two lens
   passes** (adversarial and the precedence→appeal-hold verification-gap seam). Unlike most
   deferred scope in this epic, this one is not recorded anywhere in `deferred-work.md` or in
   spec-4-4's own Boundaries/Acceptance Criteria — it reads as silently dropped rather than
   knowingly deferred, and it directly contradicts `EXPERIENCE.md`'s own stated reason for the
   rule ("an old photo proves nothing").

**Confirmed by direct re-inspection — fix now, lower urgency (real test gaps, no live data at
risk):**

4. `appeal_hold_penalty()`'s two eligibility guards — `s.verdict = 'failed'`
   (`supabase/migrations/20260824150000_an_appeal_reads_the_day_that_stands.sql:68`) and
   `carries_penalty` required (same file, lines 60-62) — are real, present code with **zero test
   coverage** of their refusal path. Confirmed via the grep the verification-gap seam ran (no
   test asserts either refusal message); a regression deleting either clause would ship with the
   full SQL suite green. (Verification-gap, precedence→appeal-hold seam.)
5. `rule_appeal()` and `mark_penalty_collected()` deliberately use `role_from_table()` instead of
   `role_from_token()` specifically to close the stale-JWT-after-demotion risk for these two
   money-moving writes — but **no test has ever made the token claim and the `profile.role` row
   disagree** for a caller of either function. Every fixture that reaches them keeps token and
   row in agreement. A regression swapping either gate back to `role_from_token()` would pass
   every existing test. (Verification-gap, referee-auth→ruling/collection seam — well-evidenced,
   confirmed the SQL suite genuinely runs in CI so this is a missing assertion, not an unrun
   test.)
6. `lib/ledger.ts`'s pill logic and `components/ledger.tsx`'s aria-label both check
   `verdict === 'expired'` before checking Penalty state — a Penalty that reaches `collected` (or
   `voided`) on a day whose settlement verdict is `expired` would still render/announce as
   "Expired," hiding that the debt was actually paid. (Edge-case-hunter.)

**Plausible, lower confidence — worth a defensive fix but reachability is unclear on my own
re-reading:**

7. Nothing stops attaching an `auto_check_kind` to a `daily_hours_quota` commitment
   (`commitment_auto_check_not_on_abstain` only excludes `kind = 'abstain'`, never checks
   cadence). However, re-reading `auto_check_pending()` and `commitments_owing()`
   (`supabase/migrations/20260820140000_weekly_quota_is_not_judged_daily.sql:45`) directly: a
   `daily_hours_quota` commitment is excluded from `commitments_owing()` entirely, so neither
   `settle_day` nor `settle_week` ever calls `auto_check_pending()` for one — that cadence
   settles purely from banked Focus-Session minutes and never consults `declaration`. The
   practical exploit path the adversarial lens describes (AD-13's settlement-gating promise
   having "zero enforcement" for this combination) may therefore be inert in practice, not
   reachable the way it is for `daily`/`weekly_quota`. A defensive DB constraint
   (`cadence <> 'daily_hours_quota'`, mirroring the existing `abstain` exclusion) is still cheap
   and removes the ambiguity outright. (Adversarial, disposition downgraded after direct
   re-check.)

**Deferred (real, lower value, recorded for a future pass):**

8. Two independently-machine-missed commitments on the same day: only the first Appeal can ever
   hold that day's one bundled Penalty (FR-13's per-day model); the second gets an
   undifferentiated raw exception with no distinguishable UX state and no retry-after-first-
   resolves path. (Adversarial.)
9. `pair-referee`'s CORS header is a wildcard (`*`), and if its one-time-password response never
   reaches the browser after the account row is already created (network drop, crash), there is
   no recovery path — `profile_single_referee`'s uniqueness permanently blocks creating another.
   (Adversarial.)
10. The `appeal_evidence` insert policy doesn't check the parent Penalty is still `held` before
    accepting a new upload — low severity since there's no re-open flow anyway, so a late upload
    is inert rather than harmful, just confusing to the author. (Adversarial.)
11. The `appeal-evidence` Storage bucket's size/MIME constraints exist only in `config.toml`
    (CLI-applied on local reset/start), not in a migration — a disaster-recovery rebuild
    following this repo's own documented source of truth (migrations) would produce an
    unconstrained bucket. (Adversarial.)
12. A `null`/unmatched Auto-check result silently falls through to "file nothing" by the absence
    of a matching `if`, not by an explicit early return (Story 4.3 replaced Story 4.1's single
    defensive guard with two positive branches). Confirmed **not reachable in production today**
    — `auto_check_kind` is a single-value enum and `resolve_auto_checks()`'s `case` always
    matches it, so `result` is never null. Worth strengthening the test suite (no fixture ever
    feeds `null`/`unavailable` into a `carries_penalty = true` commitment) before a second
    Auto-check kind is ever added, so a future "simplification" back to one negative branch would
    be caught. (Verification-gap, unavailable/missed→precedence seam — thoroughly evidenced.)

## Acceptance verdict

**Accepted-with-open-items.** Criteria: **declared** (FR-2a, FR-8, FR-8b, FR-14, FR-15, FR-19,
FR-20, FR-21, each story's own frozen Intent + Acceptance Criteria per `epics.md`). All 7 stories
are `done` (`pending_stories` empty), and every story's own individual acceptance criteria are met
by the evidence available — extensive per-story review (2-4 independent layers each, per their
own specs), a clean `tsc`/`eslint`/`npm test` (981/981) this run, and all migrations confirmed
live on the production project with no unexpected security-advisor findings.

Not **accepted** outright because this run's diff-scope review found three **confirmed** defects
(A1-A3) that a person building trust in this product would reasonably call blocking: a live,
UI-reachable way to make a genuinely machine-filed miss evade FR-2a's entire precedence
guarantee; a documented product invariant (Appeal auto-resolves when the Penalty toggle turns
off) with zero implementation; and a safety rule (FR-14's same-day-evidence-only requirement)
that is completely unenforced and was never even recorded as deferred. None of these were
previously known — unlike Epic 5's own three confirmed findings, none of these landed in
`deferred-work.md` under a "known, accepted for now" banner.

Not **rejected** because none is architecturally invasive: each has a narrow, already-sketched
fix (a snapshot-read change, one new trigger, one new column plus two checks), no story's
individual acceptance criteria are in question, and nothing here indicates rework of the epic's
actual design. Action items 1-3 are the condition for a clean **accepted** status; items 4-6
should follow soon after since they are cheap test-coverage additions closing real, live gaps in
