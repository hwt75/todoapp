## Findings

### Cross-story correctness

1. **A historical Penalty can be collected while its current replacement remains
   owed — fix now.** `object_to_day()` copies an owed Penalty into its correction
   without joining the collector's account advisory-lock protocol
   (`supabase/migrations/20260903140000_the_referee_may_object.sql:531,669`).
   `mark_penalty_collected()` later updates any named owed row without requiring its
   settlement to remain current
   (`supabase/migrations/20260826120000_the_lock_the_collector_never_took.sql:49,66`).
   A local rollback probe reproduced the sequential stale-screen path: collecting
   the original id succeeded and changed it to `collected`, while
   `penalty_current` still contained one 500,000-dong `owed` replacement. The same
   missing shared lock permits a concurrent collection between the objection's read
   and copy. One remediation should make correction and collection share the account
   lock and refuse a Penalty from a superseded settlement.

2. **An Appeal ruling can undo an earlier objection on another commitment — fix
   now.** `object_to_day()` correctly copies frozen outcomes
   (`20260903140000_the_referee_may_object.sql:632-651`), but `rule_appeal()` still
   rebuilds the day from `commitments_owing()`
   (`20260826110000_the_long_view_including_whether_this_still_works.sql:232`). An
   approved Appeal after an objection can restore the objected commitment to held.
   This interaction was already recorded in `deferred-work.md:959`; Epic 6 makes it
   a concrete boundary between two correction writers, so it is promoted to the
   next-work list.

3. **A queued timed claim can change meaning before it flushes — fix now.** The
   offline item remembers `answeredAt` and `timed`, but the insert sends only the
   timestamp (`lib/declaration-write.ts:69-78`). The database derives same-day versus
   previous-day semantics from the commitment's live `due_time`
   (`20260828140000_a_claim_lands_on_the_day_it_was_made.sql:50-79`). If another
   device clears the time before reconnection, a same-day timed claim can silently
   land on the previous day. The server needs a verifiable snapshot of the action's
   intended mode or an explicit stale-action refusal.

4. **Leaving Today during an upload can strand valid proof — fix now.** After the
   Storage upload resolves, `components/today.tsx:490` returns on unmount before it
   inserts the `evidence` row at line 500. The object exists but the photo cannot
   prove the timed claim. Keep the metadata write independent of React component
   lifetime; guard only state updates. This also gives the already deferred orphaned
   object problem a concrete user-visible trigger.

5. **Reminder enqueue and claim cancellation are not serialized — fix with Story
   6.6 before acceptance.** The enqueuer checks for a declaration before inserting
   the outbox row (`20260903090000_the_reminder_lands_inside_the_window.sql:226-287`),
   while the declaration trigger cancels independently at lines 629-659. A claim can
   commit after the check but before the insert, leaving a reminder for an already
   claimed day. Both paths need the same commitment-day lock and a regression that
   exercises the ordering.

7. **Kept-photo reads can silently truncate above the API row cap — defer.**
   `readKeptPhotos()` chunks dates but does not paginate rows

   1,000 rows (`supabase/config.toml`). This is real but remote for a single-user app
   and is recorded in `deferred-work.md`.

   update.** Story 6.1, 6.2 and 6.3 frontmatter still says `approved`, while sprint
   status says `done`. Later story files use `done`. This did not hide the current
   unfinished story, but it makes frontmatter an unreliable work-queue cross-check.
