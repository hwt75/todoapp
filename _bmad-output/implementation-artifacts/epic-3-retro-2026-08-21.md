# Epic 3 Retrospective — Work with no finish line, and weeks that hold

## Epic summary

**Goal.** Let the author commit to time rather than completion (Focus Sessions banking minutes
against a Daily Hours Quota), and close the two cadences Epic 2 left open: a weekly quota that
grows louder as sessions remaining approach days remaining, and a week that settles at its own
boundary. A Settings surface opens the epic, because every reminder the later stories schedule
follows the morning hour it exposes. **FRs covered (per `epics.md`):** FR-2 (quota), FR-4, FR-5,
FR-11, FR-12, FR-23.

**Outcome, in one line: the mechanism is built, tested against a real database, and provably not
yet deployed to the one database the app actually talks to.** Focus Sessions bank minutes
correctly across app kill/lock/background; the weekly-quota pill reads a shared counting function
also used by settlement (AD-8); Week Close runs as one idempotent `pg_cron`-invoked
transaction. All of it is verified against a locally reset Postgres — none of it exists yet on
the live Supabase project (see Finding F1).

## Findings

### F1 — Eight migrations, including the entire Epic 3 schema, were never pushed to the live project
**Severity: high. Disposition: fix now.**

`mcp__supabase__list_migrations` against project `hxzalpnlrunctbajgtkv` ("todoapp", the only
project on the account) returns 20 applied migrations, the newest being
`20260819102855_gate_chain_uuid_aggregate`. The repository has 28 migration files; the 8 missing
from the remote are every file dated `20260820*` — the tail end of Epic 2's own late review fixes
(`chain_calendar_reads_the_correction`, `outbox_body_rule_where_it_runs`,
`supersession_freezes_the_day`, `close_penalty_amount_exposure`) **and all five of Epic 3's own
migrations** (`a_session_lands_on_the_day_it_started`, `a_prompt_reads_the_view_it_was_promised`,
`the_week_counts_its_own_days`, `weekly_quota_is_not_judged_daily`, `the_week_closes_and_settles`).

`README.md`'s own "Applying migrations" section documents the step (`npx supabase link` +
`npx supabase db push`, followed by re-running the security advisor) — it was not run since
2026-08-19. Consequence: `focus_session`, `focus_day_minutes`, `weekly_quota_progress`,
`settle_week()`, and every Epic-3-era fix to `settle_day()`/`supersede_expiries()` do not exist on
the database the deployed app actually queries. Any client code path that reaches them
(`components/focus-session.tsx`, the Today pill's `weekly_quota_progress` read, Week Close) would
error against production today.

Confirmed low blast radius right now, not zero risk going forward: `select count(*) ... group by
cadence` against `public.commitment` on the live project returns **zero rows** — there is no live
commitment of any cadence yet, so nobody has hit this. `get_advisors(type=security)` also returns
no lints on the current (Epic-2-era) schema.

Every "verified end to end" claim in the Epic 3 specs and in `deferred-work.md` (the
`commitments_owing()` weekly-quota bug fix, the parallel-read error-swallowing fix, all fourteen
`supabase/tests/*.sql` files) was verified against a **local** `supabase db reset`, including in
this retrospective's own behavior check — never against the deployed project.

**Action:** run `npx supabase db push` against `hxzalpnlrunctbajgtkv` before promoting any Epic 3
story past `review`, then re-run the security advisor per README's own instruction. Consider a
`supabase migration list --linked` check (or equivalent) as a documented pre-promote step, or a
gate wired into `db-tests`, so remote drift is caught before "review", not discovered in a
retrospective.

### F2 — FR-4's actual mechanism (escalating reminders) has no owning story
**Severity: moderate. Disposition: spec reconciliation (propose).**

Story 3.3's own spec (`spec-3-3-a-weekly-quota-that-counts-down.md:36,90,177-180`) explicitly
splits "the escalating reminder that also reads this view (FR-4)" out of its scope, at the
author's request, and defers it: `deferred-work.md`'s corresponding entry says it "needs its own
migration additions... and its own literal copy... before it can be built" and should "carry
forward into whichever spec builds it next." No later story — not 3.4, not the Epic 4/5 backlog —
currently claims it. Confirmed structurally: the only `cron.schedule` call across
`20260820140000_weekly_quota_is_not_judged_daily.sql` and
`20260820150000_the_week_closes_and_settles.sql` registers `settle-weeks`; there is no reminder
job.

This leaves Story 3.3's own second acceptance criterion — "**When** reminders are generated,
**Then** their frequency and urgency increase, per FR-4" — genuinely unmet (no reminder is ever
generated for a Weekly Quota commitment), and `epics.md`'s FR coverage table (line 201: "FR-4 |
Epic 3 | Quota-aware escalating reminders") overstates what shipped: only the Today pill's
position/urgency color exists.

**Action (proposed, not applied):** either open a story to build the deferred pipeline (the design
— silent → once-daily → twice-daily, keyed on `slack = days_remaining − sessions_remaining` — is
already fully specified in the deferred-work.md entry, ready to carry forward), or amend the
`epics.md` FR-4 row to distinguish "pill built" from "reminder pipeline deferred" so the table
stops overclaiming. Human decides which.

### F5 — Third consecutive epic rejected on the same procedural gap, and it is now inconsistent within one epic
**Severity: moderate (process). Disposition: fix now + escalate the prevention.**

Epic 1's retro flagged unpromoted stories (item-4, still `open`); Epic 2's retro flagged the same

and 3.4, built *later* in the same epic, were correctly promoted to `done`. So within this single
epic, the practice was inconsistently applied rather than absent. The evidence that 3-0, 3-1, and
3-2 actually finished review is present (code-review-closing commits `7ee2811`, `5daf0a2`, and
`59e7c6d`/`3c8d073` respectively — the last two include a code-review pass plus the CI job and the

unfinished work.

**Action:** promote `3-0`, `3-1`, `3-2` to `done` (subject to `hwt75` confirming review sign-off
happened — the retrospective's own evidence supports it). Given this is the third time the same
gap has been raised, consider replacing "raise it again" with a small enforced check (e.g. a
sprint-planning validation, or a habit of flipping status in the same commit that closes a
story's review) rather than a fourth retro item.

### F6 — The one live-data risk this epic surfaced is verified moot
**Severity: informational.** Story 3.3 found and fixed a pre-existing Epic-2-era defect:
`commitments_owing()` did not exclude `weekly_quota` the way it excluded `daily_hours_quota`, so
any Weekly Quota commitment with `carries_penalty = true` could be charged a real penalty on a
single mid-week `slipped` day or silent expiry — directly contradicting FR-2. The fix
(`20260820140000_weekly_quota_is_not_judged_daily.sql`) is not retroactive, and `deferred-work.md`
flagged checking for any penalty charged before the fix landed. Queried directly against the live
project: `public.penalty` has **zero rows** dated before 2026-08-20, and `public.commitment` has
**zero rows of any cadence** — nobody has used the product yet in a way this bug (or F1) could have
reached. Nothing to reverse.
